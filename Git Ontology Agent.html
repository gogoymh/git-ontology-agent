Git Ontology Agent

Git records who changed what and when.
The ontology tracks what depends on those changes and how to merge them.

You can change a request while Git Ontology Agent is working on it. Add a budget, correct a detail, or ask a separate question. The agent replies from the state it has committed so far, then writes the final answer from the merged result.

01What it does

Git Ontology Agent (GOA) opens a branch for a new task. A follow-up that changes the task updates that branch. A separate question gets its own branch and can finish while the first task is still running.

A trip plan, a budget, and a separate question

R1 · “Can you plan my business trip to Busan next week?”
req/1Pick a KTX train and commit three hotel options.
R2 · “One more thing: keep it within ₩500,000.”
ChoiceAdd constraint.budget to req/1. Recheck the hotel options and total. Keep the train.
Interim 1 “I’ve settled on the Tuesday morning KTX. I’m checking hotels again to stay within ₩500,000.”
R3 · “What time is tomorrow’s meeting again?”
ChoiceOpen req/3 from main and merge it once the meeting question is answered.
Interim 2 “Tomorrow’s meeting is at 2 p.m. I’m still working on the trip.”
req/1Pick a hotel, confirm the total, and merge the itinerary into main.
Final “Take the 8 a.m. KTX on Tuesday and stay two nights at Hotel A for ₩180,000. The trip comes to ₩460,000, within the budget you added.”
TermMeaning
mainThe merged conversation state.
Request branchA task in progress, named req/<number>.
Base commitThe commit on main the branch started from.
ClaimOne typed piece of work state, such as trip.city or constraint.budget.
RelationHow the latest message affects a task in progress.

02Timeline

R2 changes the trip branch. R3 runs on a separate branch and merges first.

The first interim reply uses the latest commit on req/1, which has the new budget and the confirmed train. The second comes from the merged meeting result. Once the trip branch merges at M, the final reply uses that merged state to report the itinerary and identify what changed after C0.

03What the ontology tracks

GOA stores work as typed claims in state.yaml. A claim records which request it came from (from), what it depends on (depends_on), and where it stands (status).

Claim typeWhat it holdsExample
RequestA user message and its request IDreq.2 “Keep it within ₩500,000.”
ConstraintA condition the result must meetconstraint.budget = ₩500,000
AssumptionA premise the work relies ontrip.city = Busan
FindingSomething the agent has checkedhotel.candidates = three hotels
DecisionA choice the agent has madeplan.hotel = Hotel A
ProgressThe state of a work stepstep.hotel = comparing options

- {"id": "plan.train", "type": "Decision", "value": "Tue 08:00 KTX", "from": "req.1", "status": "confirmed", "depends_on": ["trip.city"]}
- {"id": "hotel.candidates", "type": "Finding", "value": ["Hotel C", "Hotel B", "Hotel A"], "from": "req.1", "status": "invalid", "depends_on": ["trip.city", "constraint.*"]}

① What to redo

When a claim changes, GOA follows its dependency links and marks affected results as invalid so the task can recompute them. In this example, the budget affects the hotel options, hotel choice, and total. Changing the city also affects the train.

② How claims merge

Git supplies the history and merge base. GOA compares the claim values and applies rules for each type.

Claim typeRuleExample
ConstraintKeep distinct conditions together.A ₩500,000 budget and a morning departure.
AssumptionPrefer an explicit correction when only one side supplies one.Change the destination to Daegu.
DecisionPrefer the recomputed value when the other side is invalid.Pick a hotel under the new budget.
FindingUse the more recent finding.A later check finds the train is sold out.
ProgressKeep it on the task branch.Comparing hotels.
RequestPreserve request records by ID.req.1, req.2, and req.3.

③ What the agent can say

StatusHow it appears in a reply
confirmed“I’ve settled on the Tuesday morning train.”
in_progress“I’m checking hotels again.”
invalidLeave out the hotel options invalidated by the budget.
superseded“I changed the destination to Daegu after your second message.”
conflictShow the competing values and ask which to use.

04How it works

1
Check for open tasks Git

If no task is open, create a branch from main and start work.

2
Classify the follow-up Decision model

Decide whether the message adds information, corrects a premise, starts a separate task, cancels work, or asks for progress.

3
Send an interim reply LLM

Use the latest committed state for a follow-up. For a separate task, reply when its result is ready.

4
Commit each work step LLM Ontology

Store results as claims. When a claim changes, redo the work that depends on it.

5
Merge into main Git Decision model

Compare claims against the merge base and apply the rules for each type. Keep competing values when the rules and decision model leave a conflict unresolved.

6
Send the final answer LLM

When work is complete, write the final answer from the merged state and identify changes introduced by later requests.

05Classifying follow-ups

The decision backend returns a typed choice. It sees the new message, the work in progress, and clues from claims the message may affect. Typesafe Jev is one supported backend.

KeyRelationExampleEffect
k1Supplement“Keep it within ₩500,000.”Add the condition to the open branch and redo the affected steps.
k2Correction“The trip is to Daegu.”Replace the destination claim and invalidate its dependents.
k3Independent“What time is tomorrow’s meeting?”Open a separate branch. Reply when it merges.
k4Cancel“The trip’s off. You can stop.”Close the branch and keep its history under cancelled/. Confirm the cancellation.
k5Progress“How far along are you?”Reply from the latest commit on the task branch.

Example Jev request

{
  "model": "typesafe/jev-1.14",
  "state": {
    "in_progress": "R1: Plan my business trip to Busan.",
    "new": "Keep it within ₩500,000.",
    "touches": [
      "Constraint"
    ]
  },
  "questions": {
    "relation": {
      "type": "choice",
      "instructions": "How does the new request relate to the request in progress?",
      "criteria": {
        "k1": "Adds a condition or detail",
        "k2": "Corrects a premise",
        "k3": "Starts a separate task",
        "k4": "Cancels the task",
        "k5": "Asks for progress"
      }
    }
  }
}

The option IDs stay neutral, with the meaning in their descriptions. This follows guidance on avoiding label bias in choice questions (arXiv 2609.26758). When several tasks are open, a second choice identifies the target. If the relation confidence falls below the default of 0.8, the agent asks for clarification: “Should I apply this to the trip plan or handle it separately?”

06Interim and final answers

Interim answer

  • Use the latest relevant commit to say what is settled, what the follow-up changed, and what is still underway.
  • For a separate task, reply from its merged result while other work can continue.

Final answer

  • Answer the original task from the merged state. Use claim provenance to identify changes from later requests.
  • Show both values when a conflict needs the user’s decision. Include a separate task’s result only if it affects the final answer.

07Merging claims

GOA runs a three-way merge over the base commit, main, and the request branch.

  1. Take a change made on one side or agreed on by both sides.
  2. Apply the rules for the claim type when the sides changed it differently.
  3. For a competing assumption or decision the rules leave unresolved, ask a typed yes/no question (noul): does the later request change the intent of the earlier one? At or above the default threshold of 0.7, take the later value. Otherwise keep both and ask the user.

The task processes invalidated work before it finishes. Cancelled branches stay out of main. The two thresholds are recorded in policy.yaml.

08Commit records

Commit trailers tie work back to the request and the branch base. For a classified follow-up, they can also record the decision model, its confidence, and which claims became invalid.

constraint.budget: add (₩500,000)

Request: req.2
Relation: k1 supplement (confidence 0.94)
Branch: req/1
Base: C0
Invalidates: hotel.candidates
Decision-Model: typesafe/jev-1.14

GOA also stores replies as commits on answers. An interim reply records the branch and commit it used. A final reply points to the merge commit. Use git show <sha>:state.yaml to inspect the state behind a reply.

09More examples

Changing the destination

R1 · “Can you plan my business trip to Busan next week?”
req/1Check trains from Seoul to Busan and commit three hotel options.
R2 · “Sorry, the trip is to Daegu.”
ChoiceClassify it as a correction (0.91). Replace trip.city and mark the Busan train and hotel results invalid.
Interim “I’ve changed the destination to Daegu. I’m checking trains and hotels there now.”
req/1Check the Seoul–Dongdaegu route, pick a hotel, and merge the revised plan.
Final “For Daegu, take the 8:30 a.m. KTX from Seoul to Dongdaegu on Tuesday. Hotel B is ₩160,000 for two nights. I changed the destination after your second message.”

Checking progress, then cancelling

R1 · “Can you plan my business trip to Busan next week?”
R2 · “How far along are you?”
ChoiceClassify it as a progress question (0.96) and read the latest task commit.
Interim “I’ve settled on the Tuesday morning train and I’m comparing three hotels.”
R3 · “The trip’s off. You can stop.”
ChoiceClassify it as a cancellation (0.95) and archive the branch at cancelled/req/1.
Interim “I’ve stopped working on the trip. The train and hotel options are still in the task history.”
With no remaining task to merge, the cancellation confirmation is the last reply.

10Scope

This design covers a single agent and its Git-backed conversation history. Long-term memory across sessions, coordination across multiple agents, and connectors to external files or databases are outside its scope.
